1. What Is Web Accessibility?

Web accessibility means building websites so that as many people as reasonably possible can perceive, understand, navigate, and interact with them — regardless of their abilities or circumstances.

Who Benefits

  • Visual — blind, low vision, colour blindness. Use screen readers and magnifiers.
  • Auditory — deaf or hard of hearing. Rely on captions and text alternatives.
  • Motor — limited hand movement. Use keyboard-only, switch access, or voice control.
  • Cognitive — dyslexia, ADHD. Benefit from clear language and consistent structure.
  • Temporary — broken arm, eye infection. Same barriers as permanent conditions.
  • Situational — bright sunlight, noisy room, slow connection.

Key idea: Accessibility benefits everyone, not only people with permanent disabilities.

2. Why Accessibility Matters

  • Improves usability for all users — captions help people in noisy environments, clear headings help everyone scan.
  • Forces correct semantic HTML, meaningful labels, and logical structure — improving code quality.
  • Required by law in many jurisdictions (ADA in the US, European Accessibility Act in the EU).
  • Accessibility and good UX reinforce each other — solving one often improves the other.

3. Accessibility and Semantic HTML

Native Elements Are Accessible by Default

A <button> is keyboard focusable, activatable with Enter/Space, and announced as "button" to screen readers — for free. A <div> has none of these.

<button>Save Job</button>
<div>Save Job</div>

Tab skips the div. A screen reader hears "Save Job" with no role — no indication it is interactive.

Semantic Landmarks Enable Navigation

<header>...</header>
<nav>...</nav>
<main>...</main>
<aside>...</aside>
<footer>...</footer>

Screen reader users jump directly between landmarks. A <div>-only page provides none of this navigation.

4. Keyboard Accessibility

Essential Keys

  • Tab — move focus forward
  • Shift+Tab — move focus backward
  • Enter — activate link or button; submit form
  • Space — activate button, toggle checkbox
  • Arrow keys — navigate radio buttons and dropdowns

All work on native HTML controls without JavaScript.

Native vs div

<button>Apply Now</button>

Tab reaches it. Enter/Space activates it.

<div>Apply Now</div>

Tab skips it entirely. Keyboard users can never reach it.

Rule: Anything possible with a mouse should also be possible with a keyboard when user input is required.

5. Focus Fundamentals

What Focus Means

Focus is the state of an element when it is the current keyboard target. Only one element has focus at a time. Natively focusable: <a href>, <button>, <input>, <textarea>, <select>. Generic <div> and <span> are not focusable.

Focus Order — Job Portal

Search field → Location field → Search button
    → Job Type filter → Experience filter
    → Job result 1 "Apply" → Job result 2 "Apply"

Focus order follows document order. If HTML order and visual order differ (via CSS), keyboard navigation becomes unpredictable. Focus must never disappear unexpectedly.

6. Screen Readers

What Is a Screen Reader?

Software that reads page content aloud or to braille. Used by blind and visually impaired users. Examples: NVDA, JAWS, VoiceOver, TalkBack. Processes the accessibility tree — not the visual screen.

Semantic vs Non-Semantic

Semantic version:

<main>
    <h1>Available Jobs</h1>
    <article>
        <h2>Java Developer</h2>
        <p>Full Time, Bangalore</p>
        <button>Apply Now</button>
    </article>
</main>

Announced: "Main region. Heading level 1: Available Jobs. Article. Heading level 2: Java Developer. Full Time, Bangalore. Apply Now, button."

All-div version: "Available Jobs. Java Developer. Full Time, Bangalore. Apply Now." — flat text, no roles, no structure.

Screen Reader Navigation Shortcuts (only work with semantic HTML)

  • H — next heading   L — next landmark   B — next button   F — next form field   T — next table

7. Accessibility Tree — Basic Concept

DOM vs Accessibility Tree

The browser builds the DOM from HTML, and also the Accessibility Tree — a simplified parallel structure containing only accessibility-relevant information. Assistive technologies read the accessibility tree, not the visual screen.

Core Properties

  • Role — what it is: "button", "link", "heading", "text field"
  • Name — its label: "Apply Now", "Email Address"
  • State — condition: "checked", "disabled", "required"
  • Value — current value: text in a field, selected option

Native HTML provides all four automatically. <button>Apply Now</button> = role "button", name "Apply Now".

Note on ARIA: ARIA adds/overrides accessibility tree properties for complex components where native HTML is insufficient. It should never replace native HTML semantics. ARIA is covered separately.

8. Accessible Names

Sources of Accessible Names

<button>Apply Now</button>

Name from text content: "Apply Now"

<label for="email">Email Address</label>
<input id="email" type="email">

Input name from label: "Email Address"

<img src="logo.png" alt="ABC Technologies">

Image name from alt: "ABC Technologies"

Meaningless vs Meaningful Names

<button>Click</button>
<button>Here</button>
<button>Apply for Java Developer position</button>
<button>View Senior React Developer job</button>

Screen reader users navigating by buttons hear a list of all button names. "Click, Click, Click" is useless. Descriptive names are essential.

9. Headings and Accessibility

Correct Hierarchy

<h1>Job Portal</h1>
    <h2>Search Jobs</h2>
    <h2>Latest Jobs</h2>
        <h3>Java Developer</h3>
        <h3>React Developer</h3>
    <h2>Recommended for You</h2>

Common Mistakes

  • Skipping levels: h1 → h4 (creates gaps in outline)
  • Multiple h1 on one page
  • Choosing heading level for font size instead of document structure

Rule: Use one h1 per page. Use headings for document structure, not visual styling.

10. Links vs Buttons

Core Mental Model

  • Link <a href> — navigates to a new location.
  • Button <button> — performs an action within the current context.
<a href="/jobs">View All Jobs</a>
<a href="/job/java-001">View Java Developer job at ABC Technologies</a>
<button>Save Job</button>
<button type="submit">Submit Application</button>

Why This Is an Accessibility Decision

Screen readers announce roles. A link activated with Enter navigates. A button activated with Enter or Space performs an action. Mismatching element and purpose breaks user expectations. A <div> used as either is not keyboard accessible at all.

11. Images and Alternative Text

Informative Images — Meaningful alt

<img src="company-logo.png" alt="ABC Technologies">
<img src="java-badge.png" alt="Java Certified Developer badge">

Decorative Images — Empty alt

<img src="divider.png" alt="">

Empty alt="" tells the screen reader to skip the image.

Common Mistakes

<img src="logo.png" alt="image">
<img src="logo.png" alt="photo">
<img src="logo.png">

Meaningless alt and missing alt are both failures. Always include alt.

12. Forms and Accessibility

Correct Label Association

<label for="f-email">Email Address (required)</label>
<input id="f-email" name="email" type="email" required>

Screen reader announces: "Email Address, required, edit text."

<input type="text" placeholder="Enter email">

Screen reader announces: "edit text." — placeholder is not an accessible name and disappears when typing begins.

Why Input Type Matters

Correct type communicates expected data and triggers appropriate mobile keyboards: type="email", type="tel", type="date", type="number".

13. Accessible Form Grouping

Why fieldset and legend Are Needed for Radio/Checkbox Groups

Without a fieldset, a screen reader hears "Junior, radio button" — no context about what is being chosen.

<fieldset>
    <legend>Experience Level</legend>
    <label><input type="radio" name="exp" value="junior" required> Junior (0–2 years)</label>
    <label><input type="radio" name="exp" value="mid"> Mid-Level (3–5 years)</label>
    <label><input type="radio" name="exp" value="senior"> Senior (6+ years)</label>
</fieldset>

Screen reader announces: "Experience Level group. Junior, radio button, 1 of 3."

14. Accessible Tables

Tables for Tabular Data Only — Never for Layout

<table>
    <caption>Available Jobs</caption>
    <thead>
        <tr>
            <th scope="col">Job Title</th>
            <th scope="col">Company</th>
            <th scope="col">Location</th>
        </tr>
    </thead>
    <tbody>
        <tr>
            <td>Java Developer</td>
            <td>ABC Technologies</td>
            <td>Bangalore</td>
        </tr>
        <tr>
            <td>React Developer</td>
            <td>XYZ Solutions</td>
            <td>Remote</td>
        </tr>
    </tbody>
</table>
  • <caption> — accessible name for the table
  • <th scope="col"> — column headers; screen readers announce them when reading data cells
  • <thead> / <tbody> — separate headers from data

15. Language and Document Metadata

lang Attribute

<html lang="en">

Screen readers use lang to select correct pronunciation. Wrong language = incomprehensible speech. For inline language changes: <p lang="ta">...</p>

Page Title

<title>Senior Java Developer Jobs — Job Portal</title>

First thing a screen reader announces on page load. Helps users with multiple tabs open.

Poor: <title>Page</title>

charset and viewport

<meta charset="UTF-8">
<meta name="viewport" content="width=device-width, initial-scale=1.0">

charset ensures international characters are encoded correctly. viewport ensures correct mobile scaling — essential for motor-impaired users on touch devices.

16. Accessible Content

Meaningful Link Text

<a href="/job/123">Click here</a>
<a href="/job/123">View Senior Java Developer job at ABC Technologies</a>

Screen reader users navigate by links — they hear a list of all link names. "Click here" three times is meaningless.

Clear Instructions

Do not rely on colour alone: "Fields in red are required" fails for colour-blind users.

Use text: "Fields marked (required) must be completed."

Consistent Structure

Navigation in the same position on every page. Buttons with the same purpose labelled consistently. Predictability benefits cognitive disability users and everyone else.

Use Native HTML Before Custom Solutions

19. Accessibility Testing Fundamentals

Keyboard Testing

Put the mouse aside. Navigate the entire page with Tab, Shift+Tab, Enter, Space, and arrows. Verify every interactive element is reachable and operable. Detects: missing keyboard access, broken focus order, focus loss. Cannot detect: screen reader announcements, missing labels.

Screen Reader Testing

Use NVDA+Firefox (Windows) or VoiceOver+Safari (macOS). Navigate by headings, landmarks, links, buttons. Verify announcements are meaningful. Detects: missing names, incorrect roles, broken form associations. Cannot detect: visual-only issues.

Automated Tools

Tools like axe-core, Lighthouse, WAVE catch ~30–40% of accessibility issues — missing alt, missing labels, heading order, lang attribute. Cannot detect: whether label text is meaningful, logical keyboard order, usability in practice. Manual testing is always required.

Browser Accessibility Inspector

Modern browser DevTools show the accessibility tree, computed accessible names, roles, and states for any element — invaluable for verifying that HTML produces correct accessibility information.

20. WCAG — Introduction

What Is WCAG?

Web Content Accessibility Guidelines — the international standard for web accessibility published by the W3C. Most legal requirements target WCAG 2.1 Level AA. Organised into three levels: A (minimum), AA (standard), AAA (enhanced).

The Four Principles — POUR

  • Perceivable — content must be presentable in ways users can perceive. Images need alt text. Videos need captions. Content must not rely on colour alone.
    HTML example: <img src="badge.png" alt="Java Certified Developer">
  • Operable — all functionality must be operable by keyboard and without causing seizures.
    HTML example: <button> instead of <div onclick>.
  • Understandable — content must be readable and predictable. Declare language. Consistent navigation. Helpful error messages.
    HTML example: <html lang="en">, meaningful form labels.
  • Robust — content must work with current and future assistive technologies. Use valid HTML. Use semantic elements.
    HTML example: <nav>, <main>, <h1>–<h6> instead of <div> for everything.

21. Accessible Job Portal Example

This example demonstrates all fundamental accessibility concepts.

<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Find Jobs — Job Portal</title>
</head>
<body>

<header>
    <h1>Job Portal</h1>
    <nav>
        <ul>
            <li><a href="/jobs">Browse Jobs</a></li>
            <li><a href="/companies">Companies</a></li>
            <li><a href="/login">Sign In</a></li>
        </ul>
    </nav>
</header>

<main>
    <section>
        <h2>Search Jobs</h2>
        <form action="/jobs" method="get">
            <label for="keyword">Job Title or Skill</label>
            <input id="keyword" type="search" name="keyword"
                placeholder="e.g. Java Developer">

            <label for="location">Location</label>
            <input id="location" type="text" name="location"
                placeholder="e.g. Bangalore, Remote">

            <button type="submit">Search Jobs</button>
        </form>
    </section>

    <section>
        <h2>Latest Jobs</h2>

        <article>
            <h3>Senior Java Developer</h3>
            <p><img src="abc-logo.png" alt="ABC Technologies"> Full Time &mdash; Bangalore</p>
            <a href="/job/senior-java-developer-abc">View Senior Java Developer job at ABC Technologies</a>
        </article>

        <article>
            <h3>React Developer</h3>
            <p><img src="xyz-logo.png" alt="XYZ Solutions"> Contract &mdash; Remote</p>
            <a href="/job/react-developer-xyz">View React Developer job at XYZ Solutions</a>
        </article>
    </section>

    <aside>
        <h2>Related Searches</h2>
        <ul>
            <li><a href="/jobs?skill=spring-boot">Spring Boot Jobs</a></li>
            <li><a href="/jobs?skill=nodejs">Node.js Jobs</a></li>
        </ul>
    </aside>
</main>

<footer>
    <p>&copy; 2026 Job Portal</p>
    <nav>
        <ul>
            <li><a href="/about">About Us</a></li>
            <li><a href="/privacy">Privacy Policy</a></li>
        </ul>
    </nav>
</footer>

</body>
</html>

23. Senior Frontend Accessibility Perspective

Accessibility During Design, Not After

Retrofitting accessibility is expensive and incomplete. A senior developer raises concerns during design review and code review — not as a separate end-of-project phase.

Semantic HTML Is the Foundation

ARIA, JavaScript enhancements, and custom components are built on top of semantic HTML — not instead of it. Every accessibility improvement built on non-semantic HTML requires more code and is harder to maintain.

Native Controls First

A native <select> is accessible on every browser without a line of JavaScript. A custom dropdown requires significant ARIA and JavaScript to reach the same level — and most implementations never fully achieve it.

Keyboard Accessibility Is Not Optional

A senior developer treats keyboard inaccessibility as a bug. Every interactive element must be keyboard reachable and operable — including dynamically added content.

Automated Tools Find ~30–40% of Issues

They cannot detect whether a label is meaningful, whether keyboard navigation is logical, or whether a form is actually usable. Manual testing is required.

Accessibility Is a Quality Attribute

In the same category as performance, security, and maintainability. A frontend application that excludes a significant portion of users is not a high-quality application.

Accessibility and Usability Improve Each Other

Solving accessibility problems frequently improves the experience for all users. Clear headings help screen reader users navigate — and help sighted users scan. Accessible forms are clearer for everyone.

24. Interview Questions

Beginner

What is web accessibility?

Web accessibility means designing and building websites so people with disabilities — visual, auditory, motor, cognitive — can use them effectively. It also benefits people with temporary limitations and situational constraints. The goal is to remove barriers that prevent people from perceiving, understanding, navigating, and interacting with the web.

Why is accessibility important?

It ensures websites are usable by the widest possible audience. It improves usability for all users, is required by law in many jurisdictions, and is a quality attribute of professional frontend work. Solving accessibility problems often improves the experience for everyone.

What is semantic HTML?

Using elements that carry meaning about the content they contain — <nav>, <main>, <button>, <h1>–<h6>. The element name communicates its role and purpose to browsers, assistive technologies, and developers.

What is a screen reader?

Software that reads page content aloud or to braille. Used by blind and visually impaired users. Processes the accessibility tree — not the visual appearance. Examples: NVDA, JAWS, VoiceOver, TalkBack.

What is keyboard accessibility?

All interactive functionality can be reached and operated using only a keyboard — Tab/Shift+Tab to navigate, Enter/Space to activate, arrows to select. Essential for motor-impaired users, voice control users, and keyboard power users.

Intermediate

Why should native HTML elements be preferred?

Native elements provide keyboard accessibility, correct roles, correct states, and correct behaviours without JavaScript. A <button> is focusable, activatable with Enter/Space, and announced as "button" automatically. Recreating this with a <div> requires significant JavaScript and is difficult to implement fully correctly.

Why is button better than a clickable div?

A <button> is natively keyboard focusable, activatable with Enter and Space, and announced as "button" by screen readers. A <div> is not focusable, has no role, and is not interactive. Keyboard-only users cannot reach or activate a clickable div.

Why are labels important?

Labels provide the accessible name for form controls. Without a label, a screen reader hears "edit text" with no description when focusing an input. Labels also enlarge the click/tap target, benefiting all users.

Why is alt important?

alt provides a text alternative for images. Screen readers read it instead of the image. Without alt, a screen reader may read the file name or announce "image" with no description. Decorative images should have alt="" to be skipped.

What is the purpose of fieldset and legend?

<fieldset> groups related form controls into a logical unit. <legend> provides the group's name. Together they give radio buttons and checkboxes the group context that individual labels cannot provide — "Experience Level: Junior / Mid / Senior" instead of just "Junior" with no context.

Why is heading hierarchy important?

Screen reader users navigate by headings to scan pages. A logical h1→h2→h3 hierarchy creates a meaningful outline. Skipped levels create gaps. Multiple h1 elements confuse the page structure. Headings chosen for font size rather than structure produce a meaningless outline.

Link vs button — when to use each?

Link — navigates to a new location (different page, section, external resource). Button — performs an action in the current context (submit, save, delete, expand). Mismatching element and purpose breaks screen reader announcements and keyboard behaviour.

Why is lang important?

Screen readers use lang to select the correct pronunciation rules and voice profile. Without it, a screen reader may read an English page in the wrong language voice, producing incomprehensible speech for users whose system language differs from the page language.

Advanced

What is the accessibility tree?

A simplified parallel structure the browser builds from the DOM containing only accessibility-relevant information. Assistive technologies read from the accessibility tree via the OS Accessibility API — not from the visual screen. Semantic HTML produces a well-structured accessibility tree automatically. Generic divs contribute little to it.

What is an accessible name?

The human-readable label identifying an element in the accessibility tree — what a screen reader announces when focus reaches it. Sources: button text content, label element, alt attribute, caption element. Every interactive element must have a meaningful accessible name.

How does semantic HTML help assistive technologies?

Semantic elements map to accessibility roles automatically. <button> = role "button". <nav> = landmark "navigation". <h2> = heading level 2. This mapping enables screen reader navigation shortcuts, correct announcements, and predictable keyboard behaviour — all without any JavaScript or ARIA.

What can automated accessibility testing detect?

Approximately 30–40% of issues. Detectable: missing alt text, missing labels, incorrect heading order, missing lang attribute, colour contrast failures, some ARIA errors. Not detectable: whether alt text is meaningful, whether keyboard navigation is logical, whether a form is usable in practice, context-dependent issues.

Why is manual accessibility testing still required?

Automated tools cannot assess meaning, logic, or usability. A page that passes all automated checks can still be severely inaccessible. Only a human (using keyboard testing, screen reader testing, and cognitive review) can verify that the page is actually usable.

What is WCAG?

Web Content Accessibility Guidelines — the international standard published by the W3C. Defines specific success criteria for web accessibility organised into three conformance levels: A (minimum), AA (standard target for most legal requirements), AAA (enhanced). Most laws and organisational standards require WCAG 2.1 Level AA.

What does POUR mean?

The four WCAG principles: Perceivable (content presentable to all senses — alt text, captions), Operable (keyboard accessible, no seizure-inducing content), Understandable (readable language, predictable behaviour, helpful errors), Robust (valid HTML, compatible with current and future assistive technologies). A website must satisfy all four.

How would you make a complex Job Portal accessible?

Start with semantic HTML — <header>, <nav>, <main>, <article>, <footer>. Use <h1>–<h6> with a logical hierarchy. Label every form control. Group radio/checkbox with fieldset/legend. Use <button> for actions and <a href> for navigation. Add meaningful alt to images. Declare lang. Provide meaningful page titles and link text. Test with keyboard and screen reader. Use automated tools to catch remaining issues. Validate on the server regardless of client-side state.

How would you approach accessibility in a large React application?

The fundamentals are the same regardless of framework. Use native HTML elements wherever possible — React renders real HTML. Use semantic elements for structure. Ensure every form control has a label. Manage focus explicitly when content changes dynamically (modal opens, route changes). Test with keyboard and screen reader. Use axe-core in the test suite. Treat accessibility failures as bugs with the same priority as functional bugs. ARIA is needed only for complex interactive components — tabs, comboboxes, modals — where no native element exists.

25. Final Accessibility Checklist

Check each item when you are confident you understand it:

  • Understand what web accessibility means and who it benefits
  • Understand why accessibility matters for UX, code quality, and legal compliance
  • Understand how semantic HTML provides accessibility for free
  • Understand keyboard accessibility — Tab, Enter, Space, arrows
  • Understand focus — what it is, focus order, why it must not disappear
  • Understand screen readers — how they process page structure
  • Understand the accessibility tree — role, name, state, value
  • Understand accessible names — from text content, labels, alt, caption
  • Use proper heading hierarchy — one h1, logical h1→h2→h3
  • Know link vs button — navigate vs act
  • Understand image alt text — informative vs decorative
  • Create accessible forms — labels, correct types, required indicators
  • Use fieldset and legend for radio and checkbox groups
  • Understand accessible tables — caption, th, scope
  • Declare lang on the html element
  • Write meaningful page titles and link text
  • Prefer native HTML controls over custom div-based solutions
  • Recognise and avoid the 12 common accessibility mistakes
  • Understand keyboard testing, screen reader testing, and automated testing
  • Understand WCAG and the POUR principles
  • Build an accessible HTML page that demonstrates all fundamentals

You are ready for the ARIA topic when you can build the Job Portal example in Section 21 from memory, explain why each element was chosen, navigate the page by keyboard, and describe what a screen reader would announce at each step.
